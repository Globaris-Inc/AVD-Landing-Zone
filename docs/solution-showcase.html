1 · Executive summary

This repository builds the application landing zone for Azure Virtual Desktop entirely as code — composed from Azure Verified Modules (AVM), governed by Architecture Decision Records, and delivered through GitHub Actions with OIDC federation (no stored secrets). It follows the Microsoft AVD Landing Zone design guide and the Azure/avdaccelerator baseline.

It was not just written and validated — it was applied to a live subscription, verified (both session hosts Available in the host pool), then torn down. That live run surfaced a dozen real-world issues that no amount of terraform validate can catch; each was fixed and is reproducible in the repo. Section 10 walks through them — it is the most instructive part of the build.

2 · What it is & scope

In scope — the application landing zone

  • Spoke network (VNet, NSG, ASG, route table, NAT gateway)
  • FSLogix profile storage (Premium Azure Files, Entra Kerberos)
  • Key Vault (RBAC, private endpoint)
  • AVD control plane: host pool, application group, workspace, autoscale scaling plan
  • Session-host VMs (Entra-joined, agent-registered)
  • Monitoring: Log Analytics + Data Collection Rule + diagnostics
  • Shared services: Compute Gallery + Automation account
  • Remote-state backend & OIDC CI/CD

Out of scope — the platform landing zone

  • Connectivity subscription (hub, firewall, gateways)
  • Identity platform (Entra ID tenant, domain services)
  • Management subscription & central governance
  • The management-group hierarchy

These are a documented prerequisite — an application landing zone sits on top of them and never builds them.

5 · Identity & FSLogix

Microsoft Entra ID join (ADR-0003)

Session hosts are cloud-only Entra-joined via the AADLoginForWindows VM extension — no domain controllers, no Entra Domain Services deployed here. The identity_mode toggle retains entra-ds / ad-ds options for portability.

FSLogix on Azure Files

Profile containers live on a Premium FileStorage share reached over a private endpoint, authenticated with Entra Kerberos (directory_service_options = "AADKERB") — which removes the need for AD DS just to use Azure Files.

Extension ordering on each host is explicit (deploy_sequence): 1 · AADLoginForWindows → 2 · AVD-agent DSC (AddSessionHost, aadJoin) → 3 · Azure Monitor Agent. An optional toggle adds the Intune mdmId for auto-enrollment (ADR-0006).

7 · CI/CD & OIDC

8 · Governance & process

Four collaborating roles

The build runs through four subagent roles in hand-off order:

  • Cloud Solutions Architect — topology, identity/network model, ADRs
  • Cloud Engineer — modules, composition root, local validation
  • DevSecOps Engineer — workflows, OIDC, state backend, posture
  • Code Reviewer — correctness + AVM/version + security gate

Enforced review gate (not just prose)

The review/test gate is enforced by hooks, not memory:

  • .githooks/pre-commit hard-fails commits on fmt/validate errors
  • A Claude Code PreToolUse hook blocks git commit unless the exact working-tree content has a recorded code-review approval (a tree-hash stamp; any edit invalidates it)

Other guardrails: verify-before-write (every AVM module + argument confirmed against the registry before use), pin every version, one section per session, stop-and-ask on ambiguity, and a running WORKLOG.md as the cross-session source of truth.

10 · The deployment story — what a real apply taught us

The build passed terraform validate long before it could actually deploy. Static analysis checks syntax, types, and provider schemas — it cannot see runtime API behaviour, RBAC propagation, tenant policy, quota, or provider quirks. The first live apply reached 86 of 97 resources before the first real wall; here is the full set of issues and the fix for each.

#ClassSymptomRoot cause → fix
1CodeStorage rejected the deployer IP allow-list (/32)Storage ip_rules take bare IPs, not /32 (KV was stripped, Storage wasn't) → shared local.ip_rules strips /32 for both
2EnvARM writes blocked: RequestDisallowedByAzure ... MFATenant Conditional Access requires MFA for user ARM access; OIDC/federation can't authenticate a local run → authenticate locally as the service principal (federation is for CI)
3Envterraform args mangled by PowerShellWindows PowerShell 5.1 native-arg quirk → pass flags via array splat & terraform @args
4CodeKeyBasedAuthenticationNotPermitted creating the state SAShared keys disabled, but the provider polled the blob plane with key auth → storage_use_azuread = true
5CodeBlob-data role missing during the SA's post-create pollRole was scoped to the SA and created after it → moved to RG scope, created before the SA, with a propagation wait
6CodeState lock failed: BlobImmutableDueToPolicyA WORM immutability policy blocks per-apply state overwrites — even while "unlocked" → removed it; blob versioning provides recovery instead
7CodeCMK flip-flopped to Microsoft-managed keys every applyClassic azurerm SA-vs-separate-CMK-resource diff → lifecycle { ignore_changes = [customer_managed_key] }
8CodePlaceholder IDs would win over CI variables-var-file outranks TF_VAR_* → removed subscription/tenant IDs from tfvars (env-only)
9Code5× Invalid for_each argument on a greenfield planMaps keyed on apply-time-unknown values → static keys (diagnostics ×4), a static enable_asg_association bool, and one(values(...)) instead of try() for the DCR association
10Codeworkspace_id: object where string requiredAVM workspace 0.2.2 resource_id output is the whole object → .resource_id.id
11PrereqVM create 400: EncryptionAtHost feature not enabledSubscription feature not registered → az feature register --namespace Microsoft.Compute --name EncryptionAtHost
12PrereqScaling plan 400: AVD service lacks permissionGrant the Azure Virtual Desktop first-party SP Desktop Virtualization Power On Off Contributor
13PrereqVM create 409: standardDASv5Family quota = 0PoC sub has no Dasv5 quota → switched size to Standard_D4as_v4 (within the regional 10-vCPU cap)
14CodeDSC agent: Unable to connect to the remote serverAzure default outbound access is retired → session hosts had no egress → added a NAT gateway on the subnet
15CodeDSC agent: parameter 'aadJoin' cannot be foundThe "always-latest" Configuration.zip dropped aadJoin (RDS-Templates #598) → pinned Configuration_1.0.02627.270.zip (agent self-updates after registration)

The takeaway for the demo: a green plan is necessary but not sufficient. A real apply against a real tenant is the gate that catches auth/MFA, RBAC propagation, provider quirks, subscription features, quota, egress, and vendor-artifact drift. Everything above is now fixed in code and reproducible — the landing zone went from valid to genuinely deployable.

11 · Operations runbook

One-time bootstrap

cd bootstrap
terraform init && terraform apply -var-file=terraform.tfvars   # creates rg-tfstate-avd-001
# → wire GitHub repo Variables: AZURE_CLIENT_ID / AZURE_TENANT_ID / AZURE_SUBSCRIPTION_ID
# → add federated credentials (main ref, pull_request, environment:production) to the app reg

Deploy / teardown (CI — the normal path)

Actions → manual-deploy → Run workflow → pick environment (dev/prod) + action (plan/apply/destroy); for apply/destroy type the environment name to confirm. Prod pauses at the production reviewer gate.

Local (driver) deploy

cd landing-zones/avd-workload
terraform init -backend-config=../../envs/dev.backend.hcl
terraform plan  -var-file=../../envs/dev.tfvars
terraform apply -var-file=../../envs/dev.tfvars

Demo reset

Actions → cleanup-demo → type the subscription ID to confirm; optionally include the state backend. Brute-force az group delete of rg-avd-* — fast and AVD-teardown-safe.

dev ↔ prod on one PoC subscription: Central US is capped at 10 total vCPUs and dev already uses 8, so the two environments are mutually exclusive — destroy dev before applying prod. The state backend (rg-tfstate-avd-001) is a separate root and is intentionally retained across workload teardowns.
